# Slurm

## Overview

With `scheduler: slurm` in `local.yml` (the default), the lab runs Slurm 23.11 (Ubuntu 24.04 packages) on the emulated hardware. Everything except the scheduler is shared with [Kubernetes (k3s)](kubernetes.md) mode, and in Slurm mode no Kubernetes component is installed.

To switch a built lab: `make down`, change `scheduler`, `make up`. Volumes, homes and the frameworks venv are kept.

| Component | Where | Role |
|---|---|---|
| `slurmctld` | `sched-control` | controller: partition `gpu`, GPU GRES, block topology |
| `slurmdbd` + MariaDB | `sched-control` | accounting, enforced: every user needs an association with an account |
| `slurmd` | `sched-worker1`, `sched-worker2` | runs job steps on the trays, binds GPUs |
| `slurmrestd` | `sched-control`, port 6820 | REST API with JWT authentication ([REST API](#rest-api)) |
| Pyxis and enroot, Apptainer, crun (Slurm OCI), podman with scrun | trays and `sched-login` (podman: `sched-login`) | jobs in containers, with their GPUs ([Containers](#containers)) |
| munge | every cluster node | authentication between the daemons and clients |
| Client tools | `sched-login` | `sbatch`, `srun`, `squeue`, `sacct`, ... for directory users |
| topograph | systemd on `sched-control` | generates `topology.conf` from the live fabric every minute ([Topology](topology.md)) |
| prometheus-slurm-exporter, `slurm-gpu-metrics` | `sched-control` | Slurm and GPU-allocation metrics ([Monitoring](monitoring.md)) |

## How it works

| Setting | Value | Why |
|---|---|---|
| Partition | `gpu` (default), nodes `sched-worker[1-2]` | |
| Nodes | 1 socket × 4 cores, 7500 MiB, `TmpDisk` 50 GiB, `Gres=gpu:gb200:4` | matches the container limits |
| GRES | `gres.conf` with `/dev/nvidia0-3`, `Links=` NV18 all-to-all | GPU binding sets `CUDA_VISIBLE_DEVICES` |
| Selection | `select/cons_tres`, `CR_Core_Memory`, `DefMemPerCPU=1875` | jobs that do not ask for memory get a per-CPU share |
| Topology | `topology/block`, one block per NVLink partition | generated by topograph ([Topology](topology.md)) |
| Accounting | `AccountingStorageEnforce=associations,limits,qos`, `AccountingStorageTRES=gres/gpu` | GPU usage per job, user and account |
| Authentication | `AuthType=auth/munge`, `AuthAltTypes=auth/jwt` (slurmctld, slurmdbd), key `/etc/slurm/jwt_hs256.key` | munge between the daemons and clients; JSON Web Tokens for `scontrol token` and the REST API |
| Containers | `plugstack.conf` loads Pyxis; `oci.conf` runs crun through the fake driver's `nvidia-container-runtime` | `srun --container-image` (Pyxis), `srun --container` (OCI bundle), scrun |
| Jobs in containers | `proctrack/linuxproc`, `task/none`, `CgroupPlugin=autodetect` | no cgroup confinement or CPU binding in unprivileged containers |
| Scratch | `TmpFS=/scratch`; `TaskProlog` sets `SCRATCH` | `--tmp` requests node-local space |

- **GPUs in jobs.** Slurm allocates GPUs as GRES and sets `CUDA_VISIBLE_DEVICES`, so a job's CUDA programs see exactly the GPUs it was given. `nvidia-smi` in a job still lists all four GPUs of the tray, as the real one does without device cgroups (`ConstrainDevices=yes`), which the lab's containers cannot use ([Emulated GPUs](fake-gpu.md#how-it-works)).
- **Topology.** topograph turns the InfiniBand switches and each tray's NVLink domain into `topology/block` blocks, and Slurm keeps a job that fits one block inside it. After a partition change, `topology.conf` updates within a minute of the GPUs' reset (by the epilog after their next job, or by hand).
- **GPU handover.** After every job, an epilog resets the job's GPUs with `nvidia-smi --gpu-reset`, as GPUs are reset between tenants on GB200. That clears their state and applies a pending NVLink partition change.
  - It then checks that no process still uses the GPUs and none needs recovery. If the reset or the check fails, Slurm drains the node.
  - It logs to the tray's journal (`journalctl -t slurm-epilog`). `gpu_handover_reset: false` turns it off.
  - Before that it removes the job's per-job directories (`slurm_epilog_cleanup`: `/dev/shm/chassis-<job id>`, `/run/user/<uid>/chassis-<job id>`), where a job launcher keeps what must not outlive a killed job.
- **Users.** Directory users (LDAP) get an association with their account from `slurm_accounts`; jobs on the trays run as the user, with homes on `/shared`.

## Usage

From the login node (`bin/ssh login`) or straight from your machine (`bin/ssh login <command>`):

```
sinfo -N -o "%N %G %c %m %d %T"                 # nodes, GPUs, CPUs, memory, scratch, state
srun -N2 --gpus-per-node=4 nvidia-smi -L         # all 8 GPUs
sbatch examples/slurm/nvl8-hello.sbatch          # one task per GPU across the domain
squeue; sacct -X -o JobID,JobName,User,Account,AllocTRES%40,State
scontrol show topology                           # NVLink blocks
```

| Example | Kubernetes equivalent | What it does |
|---|---|---|
| `slurm/gpu-topology.sbatch` | `kubernetes/gpu-topology.yaml` | one task per tray with its 4 GPUs: Slurm topology, `nvidia-smi -L`, `topo -m`, fabric state |
| `slurm/nvl8-hello.sbatch` | `kubernetes/nvl8-hello.yaml` | 8 tasks × 1 GPU across the domain |
| `slurm/ddp-train.sbatch` | `kubernetes/ddp-train.yaml` | PyTorch DDP, 2 nodes × 4 GPUs, torchrun per node |
| `slurm/ray-cluster.sbatch` | `kubernetes/ray-cluster.yaml` | Ray head and worker on the allocation, driver on the head |

From your machine, a job script can be submitted on stdin: `bin/ssh login sbatch < examples/slurm/nvl8-hello.sbatch`. Give jobs submitted this way a name (`#SBATCH -J name`), otherwise `%x` in output paths becomes `(null)`.

### REST API

slurmrestd on the controller serves Slurm's REST API (OpenAPI `v0.0.40`, Slurm 23.11's) on port 6820, for slurmctld (`/slurm/v0.0.40/...`) and slurmdbd (`/slurmdb/v0.0.40/...`). It authenticates requests by JSON Web Token: a user gets one with `scontrol token` on the login node and sends it with their name.

```
bin/ssh login
joe@sched-login:~$ export $(scontrol token lifespan=3600)        # SLURM_JWT=...
joe@sched-login:~$ api=http://sched-control:6820; auth=(-H "X-SLURM-USER-NAME: $USER" -H "X-SLURM-USER-TOKEN: $SLURM_JWT")
joe@sched-login:~$ curl -s "${auth[@]}" $api/slurm/v0.0.40/nodes | jq -r '.nodes[] | "\(.name) \(.state) \(.gres)"'
joe@sched-login:~$ curl -s "${auth[@]}" -H 'Content-Type: application/json' $api/slurm/v0.0.40/job/submit -d '{
    "script": "#!/bin/bash\nnvidia-smi -L",
    "job": {"name": "rest", "current_working_directory": "/shared/home/joe", "environment": ["PATH=/usr/local/bin:/usr/bin:/bin"],
            "tres_per_node": "gres/gpu:1", "standard_output": "/shared/home/joe/rest-%j.out"}}'
joe@sched-login:~$ curl -s "${auth[@]}" $api/slurmdb/v0.0.40/jobs | jq '.jobs | length'
```

From your machine the API is at `http://<bridge address>.10:6820` (`endpoints.md`); an administrator token comes from the controller: `bin/ssh sched-control scontrol token username=root lifespan=3600`. Tokens are signed with `.secrets/slurm-jwt.key`; requests without a valid one get `401`.

### Containers

Every runtime NVIDIA GPU clusters use with Slurm is installed, and each gives a container its job step's GPUs and only those:

| Runtime | How a job uses it | GPUs come from |
|---|---|---|
| [Pyxis](https://github.com/NVIDIA/pyxis) 0.24 and [enroot](https://github.com/NVIDIA/enroot) 4.2 | `srun --container-image=mirror.gcr.io#library/ubuntu:24.04 ...` (also `--container-mounts`, `--container-name`, `--container-save`); `enroot import`, `enroot start` by hand | enroot's NVIDIA hook (`98-nvidia.sh`, unchanged) calling `nvidia-container-cli` |
| [Apptainer](https://apptainer.org) 1.5 | `srun apptainer exec --nv docker://mirror.gcr.io/library/ubuntu:24.04 ...`, or a SIF from `apptainer pull` | `--nv` through `nvidia-container-cli` (`use nvidia-container-cli = yes`) |
| Slurm's OCI support | `srun --container=<OCI bundle> ...`; a bundle from `skopeo copy docker://... oci:<dir>:<tag>` and `umoci unpack --rootless` | crun behind `nvidia-container-runtime` (`oci.conf`) |
| podman with [scrun](https://slurm.schedmd.com/scrun.html) | on the login node: `podman run --rm mirror.gcr.io/library/ubuntu:24.04 ...` runs as a Slurm job; `SCRUN_GPUS_PER_NODE=2`, `SCRUN_PARTITION`, ... set the job's options | as Slurm's OCI support |

`examples/slurm/containers.sbatch` runs the same step in the first three:

```
joe@sched-login:~$ cd examples/slurm && sbatch containers.sbatch
joe@sched-login:~$ SCRUN_GPUS_PER_NODE=2 podman run --rm mirror.gcr.io/library/ubuntu:24.04 nvidia-smi -L
```

How the GPUs get there, as on real GPU nodes where NVIDIA's container toolkit brings the driver into containers:

- The fake driver has its own `nvidia-container-cli` and `nvidia-container-runtime` ([Emulated GPUs](fake-gpu.md#containers)). Both bring what the tray's CDI specification `/etc/cdi/fakegpu.json` lists, the same one Kubernetes pods get: the GPUs' device nodes, the driver's libraries (preloaded, as on the tray), `nvidia-smi`, the tray's configuration, sideband, telemetry and CUDA IPC directories, and the NCCL and fabric directories of the NVLink domain.
- The fake driver counts the `/dev/nvidia<n>` it finds and does not follow Slurm's device cgroup, so each runtime gets only the step's GPUs (`SLURM_STEP_GPUS`) as device nodes: an enroot hook before NVIDIA's (`97-slurm-gpus.sh`) names them in `NVIDIA_VISIBLE_DEVICES`, the `apptainer` command does the same, with `mount dev = minimal`, and `nvidia-container-runtime` reads them from the bundle's environment. A container without GPUs gets no driver.
- Images come from Docker Hub through Google's public cache (`mirror.gcr.io`, `container_registry`), as for k3s; `docker.io` works too, rate-limited. enroot keeps images and containers on the tray's `/scratch/enroot`, Apptainer's cache is in the home on `/shared`.

Resource requests behave as on a real GPU cluster: `--gpus-per-node`, `--gpus-per-task`, `--tmp`, `--mem`; jobs share a node when resources allow. Accounts and limits are managed with `sacctmgr`; accounts come from `slurm_accounts` in `inventory/group_vars/all.yml`. With `slurm_accounting: false` there is no slurmdbd: no `sacct`, accounts or limits ([Platform: Components](platform.md#components)).

## Verification

```
bin/ssh login sinfo                                          # gpu* up, 2 nodes idle
bin/ssh login 'srun -N2 --ntasks-per-node=4 --gpus-per-task=1 bash -c "echo \$(hostname) \$CUDA_VISIBLE_DEVICES"'
bin/ssh login sacct -X -o JobID,AllocTRES%50                 # gres/gpu=N recorded per job
bin/ssh sched-control scontrol show config | grep -E 'TRES|Topology|DefMem'
```

`make test` in Slurm mode checks that:

- both trays are available
- the four examples run as `joe` and print the expected output, and every job is `COMPLETED` in accounting
- a job can reach S3
- the REST API answers with a user's token, refuses requests without one, and runs a job submitted through it
- a container sees exactly its job step's GPUs in each runtime (Pyxis, Apptainer, `srun --container`, podman with scrun), and one without GPUs has no driver
- topograph's block topology and the scheduler metrics are in place

`make test-bmc-disruptive` drains a tray, power-cycles it through its BMC and checks that slurmd registers again.

## Limitations

- Slurm 23.11 lacks the newer block-topology features (`--segment`, `BlockSizes`). It packs a job into as few blocks as possible but does not require one: with the domain split into partitions, an 8-GPU job runs across two blocks without an error. Its collectives then cross InfiniBand, as on real hardware, so it runs slower ([Emulated GPUs](fake-gpu.md#how-it-works)).
- No MIG devices as GRES: the emulated GPUs split into MIG devices ([Emulated GPUs](fake-gpu.md#mig)), but `gres.conf` lists each GPU by its device node (`AutoDetect=off`, `File=/dev/nvidia<n>`), so Slurm counts a GPU with MIG on as one `gpu` GRES like any other. A job given it sees all of its MIG devices in CUDA (one per GPU instance, as the fake driver shows a MIG-enabled GPU), and `nvidia-smi` in the job shows every MIG device on the tray. MIG devices as GRES would need `AutoDetect=nvml`, whose NVML plugin finds a MIG device's access through `/proc/driver/nvidia-caps/mig-minors` and `/dev/nvidia-caps/nvidia-cap<minor>`, which the lab cannot provide (the trays' `/proc` is the host's).
- No cgroup confinement: a job can use more CPU or memory than it asked for inside its container, and `nvidia-smi` in a job lists all of the tray's GPUs.
- The fake driver's programs and libraries need glibc in the image: `nvidia-smi` 2.34 or later (Ubuntu 22.04, Debian 12, RHEL 9 and newer), the libraries 2.33 or later. As on real GPU nodes, whose driver is built against glibc too, images without it (Alpine, distroless static) get the device nodes but cannot run the driver: NVIDIA supports glibc images only (Alpine needs `gcompat`).
- `srun --container` resolves the command on the submitting node (Slurm 23.11), so a command that exists only in the container, or at another path there, fails: run it through the container's shell (`srun --container=$b sh -c 'nvidia-smi -L'`). Pyxis has no such restriction.
- Apptainer runs through a small `apptainer` command (`/usr/local/bin/apptainer`) that starts it in a user namespace mapping the user's own uid: Apptainer looks users up by their uid outside its namespace, which in an Incus container is the host's (1000000 + uid), and otherwise finds no home directory or user. Inside the container the user has only their own group.
- scrun copies no images: podman's storage is in the user's home on `/shared` (`vfs`), which the trays read, and `scrun.lua` points the bundle's few node-local files there. Images from `podman pull` take their full size in the home.
- After a tray is powered off (e.g. through its BMC), Slurm keeps showing it `idle` until `SlurmdTimeout` (300 s) passes, and jobs scheduled on it in the meantime fail. topograph drops the unreachable tray from `topology.conf` within a minute; both recover once the tray is powered on.
- After the host is suspended, the controller marks the trays down for not responding; they come back with `scontrol update nodename=sched-worker[1-2] state=resume` (slurmd registers only when it starts).
